# Replacing EF Core with Dapper in eDC: what it would really take

*Assessment based on the eDC codebase (`dev` branch, November 2026) and a working proof of concept in this folder.*

---

## Summary

- **It is possible** to build eDC on Dapper and keep the features we have today. But a lot of what makes eDC flexible and safe today comes from EF Core *and* from our own translation framework built on top of it. With Dapper, every one of those things has to be **designed, built, tested and maintained by us**.
- **The main argument for Dapper ("EF generates bad SQL") is mostly aimed at the wrong thing.** Our slowest queries come from what we ask the database to do: computed properties pulled into every query as sub-queries, and filtering and sorting on computed values. Under Dapper the same feature needs the **same SQL shape**. The proof of concept shows this: the SQL generated by hand-built Dapper code looks like what EF generates.
- **The biggest risks are not about performance.** They are about **security** (customer-division filters that EF applies automatically today), **behaviour differences** (null handling, `All()` on empty lists) and **tenant configuration** (criteria strings stored in the database that would need a new format and a migration).
- **Recommendation:** profile first; upgrade EF Core (we are on 7.0.1); fix the worst queries at their root cause; use Dapper *alongside* EF Core for hot, fixed-shape read paths (reports, dashboards, exports). If the team still wants to move off EF Core, look at **linq2db**, which keeps a LINQ provider and has a feature that does the same job as our translation framework.

## 1. What EF Core does for eDC today

Counts are approximate (from code search) but show the scale.

| What | Size in today's code |
|---|---|
| Tables mapped as `DbSet`s | ~264 (`EdcContext` 210, `VLContext` 54) |
| `SaveChanges` calls (change tracking / unit of work) | ~960 in ~200 files |
| `ChangeTracker` / `Entry()` usage | ~260 in ~70 files |
| `Include` / `ThenInclude` (loading related data) | ~380 in ~70 files |
| `IQueryable<>` used in method signatures | ~360 in ~120 files |
| **Computed-property translations** (`translationOf.Property(...)`) | **~745 in 56 translation classes** |
| `.WithTranslations(...)` call sites | ~210 in ~45 files |
| Criteria strings parsed at runtime (`Where(criteria, translator, db)`) | ~90 call sites |
| Custom Dynamic LINQ parser (`eDC.Core/Expression/Dynamic.cs`) | 2,431 lines |
| Raw SQL already used through EF (`FromSql`/`ExecuteSql`/`SqlQuery`) | ~190 |
| Data-access security filters (Z.EF Plus `ctx.Filter<>`) | `DbFactory.cs`, applied to Order, Booking, BookingTemplate, Shipment |
| Schema management | EF migrations (still being added) |

Note: raw SQL is **already allowed** today. Nothing stops us writing hand-tuned SQL for a specific slow query right now.

## 2. The translation framework, and why it matters

eDC has a customised copy of Microsoft's `Microsoft.Linq.Translations` (`eDC.Core/LinqTranslations/`, `eDC.Infrastructure/DataAccess/Translations/`).

**What it does:** a computed property such as `Shipment.Containers` is written **once** as a LINQ expression:

```csharp
translationOf.Property(e => e.Containers).Is(e =>
    (from container in Db.JobContainers.Where(w => w.ConsolidationID == e.ConsolidationID
                                               && !string.IsNullOrEmpty(w.ContainerNumber))
     join packing in Db.JobPackLines.Where(w => w.ShipmentID == e.ID)
         on container.ContainerNumber equals packing.ContainerNumber into containerPacks
     from containerPacking in containerPacks.DefaultIfEmpty()
     where e.ShipmentType == "BRK" || containerPacking != null
     select container).Distinct()
    .Union(from container in Db.JobContainers.Where(w => w.ShipmentID == e.ID
               && (w.Source == "eDC" || w.Source == "UI"))
           select container));
```

After that, **any** query can use it as if it were a normal property: filter on it, sort on it, project it, use it inside criteria strings, use it inside other translations. At runtime, `TranslatingVisitor` replaces `e.Containers` with the expression above, and EF Core turns the whole thing into one SQL statement.

The same definitions can also be **compiled and run in memory** against already-loaded objects (the client translation map / `PropertyTranslator.Evaluate`).

**Why this is the crux:** Dapper has no expression trees and no LINQ provider. It runs SQL that you give it. Every one of the ~745 translations, and the ability to *combine* them freely at runtime, has to be rebuilt in a different form.

## 3. "EF generates bad SQL": what is actually slow

The concern is valid: some eDC queries perform badly. But the causes are mostly built into what the queries ask for:

1. **Every computed property used becomes a correlated sub-query.** A grid showing 10 computed columns becomes 10 nested sub-queries per row.
2. **Filtering and sorting on computed values.** A `WHERE` or `ORDER BY` on a sub-query result can't use an index.
3. **Row explosion from `Include`.** Joining several collections multiplies rows. Split queries are used in only 3 files.
4. **Old EF Core version.** We are on 7.0.1; EF Core 8, 9 and 10 each improved SQL generation.

The team already fights this inside the LINQ itself. `ShipmentTranslation.cs` has the comment: *"BSEDC-3422 – This translation looks complex but we had to do this way to generate better query… verify performance impact"*.

### The proof of concept shows the SQL shape stays the same

Here is the SQL produced by the **Dapper** demo for "shipments with a container whose number contains MSCU":

```sql
SELECT s.ID, s.UniqueConsignRef, ...
FROM dbo.JobShipment s
WHERE (s.CustomerDivision IN @p0)
  AND EXISTS (SELECT 1 FROM (
        SELECT jc.ID, jc.ContainerNumber, ...
        FROM dbo.JobContainer jc
        WHERE jc.ConsolidationID = s.ConsolidationID
          AND jc.ContainerNumber IS NOT NULL AND jc.ContainerNumber <> ''
          AND (s.ShipmentType = 'BRK'
               OR EXISTS (SELECT 1 FROM dbo.JobPackLines pl
                          WHERE pl.ShipmentID = s.ID AND pl.ContainerNumber = jc.ContainerNumber))
        UNION
        SELECT jc.ID, jc.ContainerNumber, ...
        FROM dbo.JobContainer jc
        WHERE jc.ShipmentID = s.ID AND jc.Source IN ('eDC', 'UI')
      ) AS c0 WHERE c0.ContainerNumber LIKE @p1 ESCAPE '\')
ORDER BY s.ID
OFFSET @skip ROWS FETCH NEXT @take ROWS ONLY;
```

This is the **same correlated EXISTS + UNION shape** EF generates from the LINQ translation. If this query is slow in production, it will be just as slow with Dapper. The real fixes are the same in both worlds: indexes, denormalised or persisted computed columns, views, or a different query design.

**Where Dapper does win:** fixed-shape queries (reports, dashboards, exports, specific endpoints) where a developer writes and tunes the exact statement by hand. EF Core already allows this through `FromSql` / `Database.SqlQuery<T>`, or Dapper can run on EF's own connection and transaction.

## 4. What we would have to build with Dapper

Each row is something we get today "for free" (from EF Core or our framework on top of it) and would have to own with Dapper.

| # | Capability today | What Dapper needs | Risk if done wrong |
|---|---|---|---|
| 1 | **Customer-division security filters** applied automatically to every Order/Booking/BookingTemplate/Shipment query (`DbFactory.cs`) | A mandatory query layer that injects the filter into every statement, **including sub-queries and navigations** | **Data leak between divisions.** One forgotten `WHERE` exposes another division's data. |
| 2 | **~745 computed properties** usable anywhere in a query | Each one rewritten as a SQL fragment, view, inline table-valued function or computed column, and registered in a field whitelist | Behaviour differences, missed edge cases |
| 3 | **Dynamic filter/sort/paging** from grids, prefilters, simple search | A SQL builder: field whitelist, parameters, nested AND/OR, collection `EXISTS`, `LIKE` escaping, stable paging | **SQL injection**, wrong results |
| 4 | **Criteria strings** in tenant config (Dynamic LINQ: `Orders.Any(...)`, `OrderItems.Where(...).Sum(Quantity)`, `Supplier.Address.CountryCode.StartsWith("BE")`) | Either a parser for that language that outputs SQL, or a **new criteria format plus a data migration** of every stored criteria string | Tenant rules silently stop matching, or fail at runtime |
| 5 | **Same logic in SQL and in memory** (client translation map, `Evaluate`) | A second C# implementation of each computed property, kept in sync by hand | Screens and rules disagree with search results |
| 6 | **Change tracking / unit of work** (`SaveChanges` ×960) | Explicit insert/update calls, dirty tracking, ordering of inserts by dependency, transactions | Lost updates, partial writes |
| 7 | **Loading related data** (`Include` ×380) | `QueryMultiple` / multi-mapping per case | N+1 query storms |
| 8 | **OData endpoints** (rely on `IQueryable`) | Remove, or rebuild OData-to-SQL translation | Broken integrations |
| 9 | **Compile-time safety**: renaming a property breaks the build | SQL in strings breaks only at runtime | Every query needs an integration test against a real SQL Server |
| 10 | **Migrations** | DbUp / FluentMigrator / SSDT | Low risk; a solved problem |
| 11 | **DB functions** (`HasDbFunction`: `DatePart`, `kfn_*`) | Plain SQL | Easy; Dapper is simpler here |

### Hidden behaviour differences (found while building the proof of concept)

These change results without any error:

- **Null equality.** EF translates C# `a == b` on two nullable columns as `a = b OR (a IS NULL AND b IS NULL)`. Plain SQL `a = b` is never true when both are NULL. The `Shipment.Containers` translation compares `ConsolidationID` this way, so a straight port changes which containers match.
- **`!=` with NULL.** In C# `x != "A"` is true when `x` is null; in SQL `x <> 'A'` is not. The demo has to write `(x <> @p OR x IS NULL)` to match.
- **`All()`.** A naïve `NOT EXISTS (... WHERE NOT pred)` skips rows where `pred` is NULL, so `All()` returns true when C# would return false. The demo needs `CASE WHEN pred THEN 1 ELSE 0 END = 0`.
- **Two conditions on one collection.** "has a container starting with MSCU" AND "has a 20GP container" is *not* the same as "has a container that starts with MSCU and is 20GP". The demo shows both give different answers (scenarios 3a and 3b). Any filter format has to express this difference explicitly.
- **Security filters inside sub-queries.** In the demo, `Consolidation.Shipments.Count()` counts shipments without applying the division filter. Each navigation needs a deliberate decision about whether the filter applies.

Every one of the ~745 translations and every stored criteria string would have to be checked for differences like these.

## 5. Proof of concept (this folder)

A working .NET 8 console app that searches `Shipment.Containers` with Dapper. It contains **20 scenarios, each checked against its expected result**, all passing on SQL Server 2022.

| File | Lines (approx.) | Replaces |
|---|---|---|
| `Search/SearchMap.cs` | 70 | `TranslationMap` + EF mapping (field whitelist) |
| `Search/ShipmentSearchMap.cs` | 60 | `ShipmentTranslation.cs` (**1 of ~745 translations**) |
| `Search/SqlFilterBuilder.cs` | 140 | EF's LINQ translator for filters, sorting and paging |
| `Search/CriteriaTranslator.cs` | 350 | `Dynamic.cs` + EF translator (**subset only**) |
| `Search/FilterJson.cs` | 50 | Reading saved filters |
| `Data/ShipmentRepository.cs` | 90 | `WithTranslations` + `Include` + division filters |

What it covers:
- Search on a computed collection, `Any`/`None`/`All`/`Count`/`Where`, same-container conditions, `IN` lists, `OR` across levels.
- Sorting on a computed value (`ContainerCount`), paging, loading related rows in one extra query (no N+1).
- Navigation to a related record (`Consolidation.TransportMode`, `Consolidation.Shipments.Count()`).
- Division filter that can't be bypassed, values passed as parameters, unknown fields rejected, syntax errors reported with their position.

What it does **not** cover (each is extra work): the other ~744 translations; `Sum`/`Min`/`Max`; `FirstOrDefault().X`; lists of plain values with an implicit `it` (`OrderNumberList.Any(Contains("x"))`); dates and arithmetic; custom fields (`CustomFields.X`); in-memory evaluation; writes; transactions; concurrency; OData.

**Take-away:** about 800 lines got **one** computed property and a subset of the criteria language working. The design scales, but the *content* (every translation, every operator, every stored criteria string) is where the work and the risk are.

## 6. Criteria format: options if we leave Dynamic LINQ

| Option | Effort | Pros | Cons |
|---|---|---|---|
| **A. Re-implement Dynamic LINQ in SQL** (extend `CriteriaTranslator`) | High | No change for existing tenant configuration | A parser and SQL generator to maintain forever; must match every syntax tenants have ever stored |
| **B. JSON filter tree** (recommended, see `FilterJson.cs`) | Low–medium | No parser; easy to check when saved; same shape as the Kendo filter descriptors the grids already send; a UI query builder can produce it | One-off migration of stored criteria; some advanced expressions (aggregates, arithmetic) need explicit operators |
| **C. OData `$filter` syntax** | Medium | A standard; a parser already exists in `Microsoft.OData.Core` (already referenced) | Needs an EDM (schema) model; different syntax to learn; still needs SQL generation |

Example of option B (scenario 20 in the demo):

```json
{ "and": [
    { "or": [
        { "field": "Containers", "op": "any",
          "where": { "field": "ContainerType", "op": "eq", "value": "20GP" } },
        { "field": "OriginCode", "op": "in", "value": ["SEGOT", "DEHAM"] }
    ]},
    { "field": "ShipmentType", "op": "neq", "value": "BRK" }
]}
```

Whichever option is chosen, the **first step** is an inventory: extract every criteria string stored in tenant configuration and run it through the new translator or converter, to see how many convert automatically and how many need manual rework.

## 7. Alternatives to a full Dapper rewrite

| Option | What it means | Fit |
|---|---|---|
| **Modern EF Core + targeted fixes** | Upgrade 7.0.1 to the current version, `AsNoTracking`, compiled queries, `ExecuteUpdate`/`ExecuteDelete`, `AsSplitQuery`, projections to DTOs, fix the heaviest translations | Lowest risk; addresses most of the real causes |
| **Hybrid: EF Core + Dapper** | EF Core for writes, the domain model and dynamic search; Dapper (on EF's connection/transaction) for hot, fixed-shape reads | Gets Dapper's speed where it matters, without rebuilding the framework |
| **linq2db** | A lightweight ORM with Dapper-like speed that keeps a LINQ provider; its `[ExpressionMethod]` attribute does the same job as our translation framework | Best option if the goal is "not EF Core" but we want to keep dynamic queries |
| **Full Dapper** | Everything in section 4 | Highest effort and risk; justified only if profiling proves EF itself (not query design) is the bottleneck |

## 8. If we do go with Dapper: minimum requirements

These are **must-haves**, not nice-to-haves:

1. **One query layer** that every read goes through. It owns the field whitelist, parameters, and the **division/tenant security filters**. Raw SQL outside it is an exception and needs review.
2. **One home for each computed property:** decide per property between a database view/function, a persisted column, or a C# rule. Don't keep two copies.
3. **A criteria format** (JSON tree recommended) and a **migration plan** for stored tenant criteria, starting with the inventory.
4. **Integration tests against a real SQL Server** for every field in the whitelist and every repository query, plus explicit tests for the security filters.
5. **Explicit transactions and optimistic concurrency** for writes, so the booking concurrency guarantees are kept (see `BOOKING-API-CONCURRENCY-HANDLING.md` and `TRANSACTIONAL-BOOKINGS.md`).
6. **A behaviour-difference checklist** (null equality, `!=` with NULL, `All()` on empty sets, same-element versus any-element conditions) applied to every translation that is ported.

---

## 9. Suggested next steps

1. **Measure.** Pull the top 20–30 queries by total CPU and duration from SQL Server Query Store, and use `TagWith` to trace each one back to code.
2. **Classify each slow query by root cause:** inlined translations, filter/sort on a computed value, row explosion from `Include`, a genuinely bad translation, or a missing index.
3. **Upgrade EF Core and re-measure** the same queries.
4. **Decide with data.** If most slow queries are fixed-shape and EF-specific, move those to Dapper (hybrid). If they're slow because of what they ask for, change the query design. Swapping the library won't fix them.
